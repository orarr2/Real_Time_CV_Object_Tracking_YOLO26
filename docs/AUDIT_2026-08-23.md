## The three visible bugs - deep dive

### Bug #1 - "Frame stuck on the screen"

**What the operator sees:** the video tile shows a static frozen
frame (or completely black) with the LIVE chip lit and CPU/RAM
climbing.

**Root cause (verified live):** on this operator IP YouTube blocks
`yt-dlp` extraction. The backend returns
`{"ok":true,"pending":true,"note":"stream unavailable - retrying..."}`.
That state can persist for the entire session. The shipped fallback is
`SCREEN_CAPTURE_FALLBACK=1` (`src/app/screen_capture.py` +
`detect_core.grab_frame` sentinel branch), but it needs:

- the operator's Chrome window with the dashboard tab to be
  foreground on the primary display
- an accurate iframe bbox posted to `/api/screen-capture/bbox`
  (frontend does this on Start via `getBoundingClientRect()`)
- YouTube autoplay policy to actually start the video (needs an
  earlier user gesture on the tab)

If any of the three fails, backend grabs the wrong region (or fails
entirely), inference runs on wrong pixels, the UI polls
`/api/analysis/frame` which 404s, and the video area stays black.

**Second, subtler cause (code-only, not verified this pass but
present in code):** in `live_analysis.py:_grab`, when a grab fails the
session falls back to a `_LAST_GOOD_FRAME` cache. If that cache is set
once and no subsequent grab succeeds, the same frame is redrawn
forever - looking like a freeze but with the tick counter still
advancing.

**Verdict:** BROKEN. Needs product-level decision. Options in the
NEEDS-CHANGE section below.

### Bug #2 - License plates repeating + wrong

**Evidence pulled live from `/api/analysis/saved`:**

- `UU730 (0.63)` at `ts=1787331505.23114`  
  `UU730 (0.63)` at `ts=1787331505.169`  
  = **62 ms apart** for the "same" plate, same conf, same cam
- `20H6863 (0.77) / 2OW6863 (0.70) / 20A6863 (0.73) / 20H0963 (0.62)`
  all within a 10-minute window - same vehicle, four different reads
- `2017 (0.63)` and `6178 (0.85)` - 4-digit hallucinations
- `104E (0.53)` on a frame that shows people on a street, no visible
  vehicle plate at all

**Root causes:**

1. **Per-track dedup only** (`PLATE_TID_DEDUP_S = 300` in
   `plates.py:120`). If the tracker re-assigns a new tid to the same
   vehicle (happens with `_plates_pass` obstruction bail-out, fast
   movement, or crossing the frame), the same plate fires again with
   no cross-tid check.
2. **OCR thresholds too permissive.** `OCR_MIN_CONF=0.45` (was 0.60)
   and `OCR_MIN_CHARS=4` in `plates.py:124-125` let short garbage
   through.
3. **Best-of-many-attempts encourages hallucinations.** For each
   buffered crop the OCR runs on `_upscale_for_ocr` AND
   `_enhance_for_ocr` and keeps the max-conf read
   (`plates.py:730-733`). A single misread with a lucky-high conf
   wins.
4. **The 62 ms exact duplicate** points to a race condition, not a
   tracker split - both writes go through
   `_emit_event("plates", auto_save=True, ...)` which reaches
   `save_event` (`live_analysis.py:3255`) that reads then rewrites
   `saved.json` without a lock. Two ticks that produced the same
   plate can both pass the per-tid dedup check between them.

**Verdict:** BROKEN. Recommendation: temporal-aggregation window
(N reads over K seconds must agree, with rank on average conf), and
a global plate-string dedup with hamming-distance tolerance for the
common `O/0`, `I/1`, `S/5`, `B/8` mix-ups.

### Bug #3 - Investigation modal (A/B/C/D "panels")

**What the operator sees on the "104E" tile:** four panels titled
"A. Vehicle crop", "B. Plate crop", "C. Enhanced plate",
"D. Final view". In the audit-time screenshot (this session): A shows
the full saved image (people on street), B/C/D show the SAME image
cropped to the bottom-center with progressively stronger contrast.
No actual license plate is visible in any panel.

In the operator's earlier screenshot from before this audit, all four
panels were BLACK (image had failed to load in time or path issue).

**Root cause (backend audit + code read):**

- The four panels are painted by `paintStages(items, panels)` in
  `src/web/app.js:1256`.
- All four canvases draw from the SAME `it.image` URL
  (`snapshots/detections/<cam>_<id>.jpg`).
- B/C/D use `drawImage` cropped to the bottom-center 70% (`by=ih*0.30`,
  line 1275) with CSS `filter` for contrast/brightness.
- The REAL per-stage crops (`vehicle_crop`, `plate_crop`,
  `enhanced_plate`) DO exist on disk at
  `src/data/plate_crops/<cam>/<ts>_<tid>_<text|UNREAD>_<conf>.jpg`
  written by `_save_plate_crop` at `plates.py:499`.
- No HTTP endpoint serves them and no JSON row in `saved.json` points
  to them.

**Verdict:** BROKEN by design. This is theater, not an investigation
pipeline. Recommendation is in the RETRIEVAL section below.

### 12 - False positives between layers

**VERIFIED (re-run agent).** Full per-layer audit against
`live_analysis.py`, `faces.py`, `plates.py`, `pose.py`, `gestures.py`,
`behavior.py`, `web/app.js`, `tracker.py`.

**Absolute truth check on the operator's Hebrew report ("face
detection made vehicles appear"):** the current code does NOT paint
vehicle boxes on the faces layer. Backend `_render` for
`layer=="faces"` (`live_analysis.py:2253-2255`) calls only
`draw_faces_layer_img(img, faces_list, ...)` on a `frame.copy()`
(`:2203`) - no `draw_boxes`, no vehicle rects. Frontend canvas
explicitly skips ALL `d.boxes` when `d.layer==="faces"`
(`web/app.js:2103`). The symptom the operator saw is textual, not
graphical: the SHARED HUD counts `data["person"]` and
`data["vehicles"]` (`live_analysis.py:2884-2888`) plus the ENVELOPE
line `"N people · M faces …"` (`:2967-2969`) always show BOTH
person and vehicle counts regardless of the active layer, which is
confusing on the faces layer even though no vehicle rectangles
appear.

**Per-layer risk table (CONFIRMED live-code trace):**

| Layer | Backend rects drawn | Frontend canvas rects | Cross-layer risk |
|---|---|---|---|
| paths | ALL classes (intentional) | ALL boxes | NONE |
| pose | none (skeletons only) | skips non-person | NONE |
| gestures | none (arrows/text only) | skips non-person | NONE |
| body | grey box on ALL persons; red on flagged | flagged persons only | NONE |
| faces | face rects ONLY | face rects ONLY (`d.boxes` skipped) | NONE |
| heat | thermal recolor, no boxes | heat colormap, no boxes | NONE |
| line | line + counter pills only, no boxes | line + counters + **ALL `d.boxes`** | POSSIBLE (backend/frontend visual mismatch) |
| parking | polygons only | polygons + **ALL `d.boxes`** | POSSIBLE (same mismatch) |
| fire | orange fire rects only | fire hits + **ALL `d.boxes`** | POSSIBLE (same mismatch) |
| plates | plate boxes + vehicle rects (filtered to `PLATE_VEHICLE_CLASSES`) | same filter | NONE |
| loiter | **NOT A LAYER** - removed per `live_analysis.py:48-50`; loiter folds into `parking` layer via `_zone_stats` | - | N/A |

**Root of the line/parking/fire mismatch:** `_publish_data`
(`live_analysis.py:2705-2726`) always ships the FULL tracker state
into `data.boxes` regardless of layer. Backend JPEG suppresses that
in the per-layer draw function, but the frontend main draw loop
(`app.js:2102`) has skip guards for `heat/pose/gestures/body/faces/
plates` and NO guard for `line/parking/fire`, so those three layers
paint generic detection boxes on the canvas that the backend JPEG
never draws. Not a class-contamination bug (boxes carry their real
`cls`), but a real UI inconsistency the operator will read as noise.

**Two more sub-findings from the re-run:**

- **Obstruction event chips are permanently invisible.** The
  obstruction pipeline (`live_analysis.py:3117-3147`) emits events
  tagged `layer="obstruction"`, but "obstruction" is NOT listed in
  `ANALYSIS_LAYER_DEFS` (`app.js:669-680`). The chip strip filter
  (`app.js:1019-1025`) hides chips whose `dataset.layer` doesn't
  match a defined layer, so obstruction chips render then get hidden.
- **`log_crossing_event`** (`live_analysis.py:581-634`) writes to
  `data/crossings/<cam>.jsonl` on EVERY layer (not just line)
  because `update_crossings` runs from `_accumulate` unconditionally
  (`:2172-2185`), and no `layer` field is written to the row. The
  file is consumed only by `/api/crossings`. Not a display bug but
  is a "line-only artefact that fires on other layers" side-effect.

- **No `cls_id` / `NAME_BY_ID` mismatch** found. The three secondary
  detectors keep separate output containers (face detector emits
  face dicts without `cls`; plates emit `plate_box`; fire emits
  `hits` with `cls="fire"`) that never mix with `self.tracker.open`
  / `js_boxes`.

Recommendation:
- Add skip guards in `app.js:2102-2109` for `line/parking/fire` so
  the canvas matches the JPEG.
- Move the ENVELOPE / HUD counts into per-layer variants (faces
  layer shows `N faces`, plates layer shows `N vehicles ·
  M plates`, etc.) so the text stops confusing operators.
- Add `"obstruction"` to `ANALYSIS_LAYER_DEFS` OR route obstruction

**Two-buffer risk: CONFIRMED.** With `SCREEN_CAPTURE_FALLBACK=0`
(default per env check `detect_core.py:114`) the browser iframe
plays a YouTube LL-HLS session while the backend pulls a SEPARATE
yt-dlp-resolved manifest through its own persistent `_StreamReader`
(`live_analysis.py:1499-1550`). The two sessions carry independent
segment offsets, ABR ladders, and buffer depths. The comment at
`live_analysis.py:2861-2871` explicitly notes that `/ytproxy` PDT
measurement was supposed to reconcile them but **`STREAM_PDT_OFFSET`
is only DECLARED (`:163`) and NEVER assigned** - `grep STREAM_PDT_OFFSET\[`
returns zero writes. So the offset always defaults to 0, and there
is **no clock-sync/seek mechanism** for youtube iframes. With
`SCREEN_CAPTURE_FALLBACK=1`, only ONE buffer feeds pixels (the
browser's), which is why the operator is instructed to keep the
iframe visible (`app.js:1533-1534`).

**FPS/latency HUD (or lack thereof):** only the inter-tick delivery
gap is shown - `hud-tick` EMA in `app.js:1583-1590` ("Xs / tick",
updated from `a._gapEma` at `:1724`). This measures the POLL-side
gap between two server publishes, NOT capture-to-render latency.
There is no "end-to-end latency" field, no per-stage timing, no
queue depth. Grepping `latency|infer_ms|tick_ms` across `src/app`
finds no runtime metric.

**Frozen-frame bug (bug #1) - MULTIPLE confirmed causes:**

- **`screen_capture.capture()` returns cached `_LAST_GOOD_FRAME` on
  ANY exception** in both the mss branch
  (`screen_capture.py:84, 100, 105`) AND the PIL branch (`:115`).
  Since a valid ndarray comes back, `LiveSession._grab` sets
  `self._fail = 0` (`live_analysis.py:1847-1848`) - no refresh,
  no invalidate, no note published. Inference then reruns on
  identical pixels; tracks look "stuck" and boxes appear frozen.
  **The screen path has NO staleness bound at all** (contrast the
  HLS path at `:1874` which DOES invalidate after 20 s without a
  new `latest_ts`).
- **The iframe pauses / ad-breaks / buffers with no signal to the
  backend.** `_syncAnalysisBgVisibility` unconditionally assumes
  `playing = true` for YouTube iframes (`app.js:1671-1673`), so the
  canvas is never hidden and the JPEG fallback never surfaces.
- **Client draw loop keeps painting `buf[buf.length - 1]` forever**
  (`app.js:1345, 1422`) - no expiry on the tick buffer. Even if
  the server returns 404/410/202, `_analysisDrawLoop` keeps
  rescheduling itself (`:1330`) and the last-drawn boxes remain on
  screen with no visual "stale" indicator (unlike the HLS non-YT
  path where `_syncAnalysisBgVisibility` swaps to the still JPEG
  when `video.currentTime` stops advancing at `:1676-1682`).
- **Backend recovery:** `IDLE_STOP_S = 60 s`
  (`live_analysis.py:86`) means the SESSION survives regardless,
  but `TICK_TARGET_S = 0.8 s` sleeps between ticks even when
  everything stalls (`:1818-1820`).

**Everything about "holy trinity" simultaneity relies on assumptions
the code does not enforce**: iframe and backend are independent
pipelines, the only clock-alignment hook (`STREAM_PDT_OFFSET`) is
unpopulated, and the only end-to-end signal to the user is a rough
inter-tick gap.

Recommendations (bumped in priority based on the re-run):
- **P0**: `_LAST_GOOD_FRAME_AGE_S` timer + red "Stream stalled"
  ribbon whenever age > 3 s. Also apply this in `_grab` (screen
  branch) so `_fail` increments after N cache-only tries.
- **P0**: parity with HLS - if the JS canvas repainted the same
  `latestTick` for > `2 * POLL_MS`, show a stale ribbon.
- **P1**: populate `STREAM_PDT_OFFSET` from the `/ytproxy` PDT
  probe the comment references, OR delete the dead reference.
- **P1**: expose `_grab_ms / _infer_ms / _render_ms /
  end_to_end_ms` next to the existing "Tick" chip.
- **P2**: fix `LIVE_IMGSZ = 512 vs 640` doc drift in
  `README.md` + `AUDIT_REPORT.md`.
- **P2**: consider `bgutil-ytdlp-pot-provider` OR residential VPN
  to unblock yt-dlp on this IP - screen-capture fallback is the
  documented workaround but it is fragile.
