- **תוכנית תיקון בת 4 חלקים:**
  - **C1a: מנעול על `save_event`.** להסיר את ה-race של 62ms. `LiveSession.save_event` ב-`live_analysis.py:3255` קורא ואז כותב את `saved.json` בלי lock. שני ticks שמייצרים את אותה לוחית יכולים לעבור את בדיקת ה-dedup לפני שהראשון סיים לכתוב. `threading.Lock()` יסגור את הפער.
  - **C1b: dedup חוצה tracks.** להוסיף `PLATE_STR_DEDUP_S = 30` (או ערך אחר לבחירתך). אם אותה string לוחית עולה מ-tid חדש בתוך 30 שניות מהפעם הקודמת - לדכא. כרגע `PLATE_TID_DEDUP_S=300` הוא רק פר-track, אז tracker split גורר reset. הוספה של lookup מבוסס string פותרת.
  - **C1c: הסכמה זמנית בין פריימים.** במקום להנפיק אחרי הקריאה הראשונה, לצבור K קריאות ל-tid (K=3 למשל) ולאשר רק אם 2 מתוך 3 מסכימות בהמינג distance <= 1. פותר את בעיית הראש והזנב של הזיות בקריאה בודדת. יגדיל את ה-latency לזיהוי אמיתי בכ-2-3 טיקים אבל יסלק את רוב ה-`104E`.
  - **C1d: dictionary לפי מדינה.** לפי המצלמה - לדעת שמצלמה תאילנדית מצפה לפורמט מסוים (תווי thai + ספרות + מחוז), טורקית מצפה ל-2 ספרות + 1-3 אותיות + 2-4 ספרות. לדחות reads שלא מתאימים. אופציונלי - נדחה לגל שני.
- **סיכון:** בינוני. יש להעריך אחרי C1a-C1c האם 0.30 עדיין נכון או שאפשר להעלות ל-0.40. אני אריץ א/ב לפני/אחרי על צילומים אמיתיים.
- **תלות:** אין.

**C2. באג #3 - LPR pipeline modal ריק/לא רלוונטי**
- **מה נמצא:** המודל מציג את אותה תמונה 4 פעמים עם CSS crops. הקרופים האמיתיים (`vehicle_crop`, `plate_crop`, `enhanced_plate`) קיימים ב-`src/data/plate_crops/<cam>/...` אבל אין endpoint שמגיש אותם.
- **תוכנית:**
  - **C2a:** להוסיף endpoint `GET /api/analysis/plate-crops?tid=X` שמחזיר את 5 הקרופים האחרונים ל-tid.
  - **C2b:** להוסיף שדה `plate_crop_paths` ב-JSON payload של אירוע plate, שיצביע לקבצים.
  - **C2c:** לחווט את פאנלים B/C/D במודל ל-URLs האמיתיים במקום CSS crops.
  - **C2d:** להוסיף גם אירועים ל-DIAG של OCR שכשל (למשל למי היה `plate_conf=0` - לראות איפה זיהוי הצליח אבל OCR נכשל).
- **סיכון:** נמוך.
- **תלות:** אין. עדיף לפני C1c כי תראה את איכות הקרופים ותוכל לכייל את סף ההסכמה בהמינג.

**C3. באג #1 - פריים תקוע: אין staleness detection**
- **מה נמצא:** 4 סיבות שורש עצמאיות (חסימת yt-dlp, screen-capture דורש טאב קדמי, `_LAST_GOOD_FRAME` בלי staleness bound, `_syncAnalysisBgVisibility` תמיד `playing=true`).
- **תוכנית:**
  - **C3a: staleness bound ל-screen path** ב-`screen_capture.py`. אם N ניסיונות רצופים מחזירים cache-only (בלי capture חדש), להעלות `_fail`. כרגע `_grab` מאפס `_fail=0` כי `capture()` "מצליח" (מחזיר cache).
  - **C3b:** באנר אדום client-side כש-`latestTick` לא מתעדכן > 2 * POLL_MS. פועל גם ב-YouTube וגם ב-HLS.
  - **C3c: `STREAM_PDT_OFFSET`** - מוצהר אבל אף פעם לא נכתב. או לממש את מנגנון /ytproxy PDT ההרמזון (`live_analysis.py:2861-2871`), או למחוק את הצהרת ה-var כדי לא להטעות.
  - **C3d: bgutil-ytdlp-pot-provider או VPN.** לצאת מחסימת ה-yt-dlp על ה-IP הזה. שני מסלולים:
    - הרצת שירות `bgutil-ytdlp-pot-provider` בצד (Node.js, מייצר PO tokens ל-yt-dlp). מורכב, יציב, יאפשר headless עם auto-restart.
    - VPN residential שלא נורה על ידי yt-dlp. פחות עבודה, יותר עלות/תלות.
- **החלטה שלך:** איזה מבין C3d תעדיף להתחיל איתו? או אולי להישאר עם screen-capture fallback כרגע?
- **סיכון:** נמוך-בינוני.
- **תלות:** אין בין C3a-C3c. C3d עצמאי.
