# מדריך הפרויקט - זיהוי אובייקטים בזמן אמת (YOLO26)

הרחבה של `README.md` בשורש הפרויקט. המסמך הזה מכסה את מסלול הריצה
בפועל, כל פרמטר תצורה שאפשר לכוונן, את המכניקה של כל אחת מ-11 שכבות
הניתוח, ואת נקודות ההרחבה להוספת מקורות, מודלים ושכבות משלך.

הקורא שלנו: מי שכבר הריץ `python serve.py` פעם אחת לפחות, ראה את
האריח החי זז, ורוצה עכשיו להבין מאיפה המספרים באים - או איך לחבר מודול
חדש.

## 1. מסלול הריצה של טיק אחד

כל מחזור עיבוד של פריים אחד (טיק) עובר את אותם חמישה שלבים. כל שלב הוא
פונקציית פייתון קטנה שאפשר לבדוק בנפרד, וכולם יושבים תחת `src/app/`.

<a id="11-פענוח-המקור"></a>

### 1.1 פענוח המקור

- **קלט:** `cam_id` שנבחר בתפריט המצלמות.
- **פלט:** כתובת סטרים לניגון או נתיב לקובץ מקומי, בתוספת רישום מטמון
  לכל מצלמה.

`resolve_stream(cam)` שבתוך `detect_core.py` מפצל לפי השדה `kind`
של רשומת הקטלוג:

| `kind`         | מה עושים |
| -------------- | -------- |
| `hls`          | הכתובת נכנסת ישירות. |
| `skyline`      | מורידים את דף ה-HTML של skylinewebcams, שולפים ה-`.m3u8` חתום מהג'אווהסקריפט המוטבע, ושומרים במטמון עד סוף תוקף הטוקן. |
| `webcamera24`  | אותו רעיון, דף ה-HTML של webcamera24 מכיל את כתובת ה-HLS במטמון הנגן. |
| `youtube`      | מריצים `yt-dlp` עם ה-android player client כדי לקבל את מניפסט ה-HLS החי. לפעמים צריך cookies מיוצאים כדי לעקוף בדיקת בוט. כאשר גם עם cookies יוטיוב חוסמת ברמת IP ומופעל `SCREEN_CAPTURE_FALLBACK=1`, ה-resolver מחזיר את הסנטינל `screen://primary` והשרת קורא פיקסלים ישירות מהמסך הראשי (ראה קטע 1.2). |
| `local_file`   | הנתיב חוזר כמות שהוא. |

הפענוחים נשמרים ב-`data/resolve_cache.json`. פגיעה במטמון היא קריאת
דיסק אחת; החטאה עולה בקשת HTTP GET אחת (ולמקרה של YouTube - גם ריצת
`yt-dlp`).

<a id="12-שליפת-פריים"></a>

### 1.2 שליפת פריים

- **קלט:** הכתובת או הנתיב שהתקבלו, ותקציב זמן קשיח.
- **פלט:** מערך BGR מפוענח אחד, או `None` בכישלון.

`grab_frame(url, timeout)` פותח `VideoCapture` של OpenCV, קופץ
לחבילה האחרונה שבזרם (זנב רשימת הסגמנטים ב-HLS או
`frame_count - 1` בקובץ), מפענח פעם אחת ומשחרר. הזמן הכולל נחסם
בקשיחות כך שמצלמה תקועה לא תקפיא את לולאת הטיקים.

מצבי כשל מדווחים כרשומת `GrabError` דחוסה:

- `kind` - אחד מ-`timeout`, `open_failed`, `decode_failed`,
  `empty_frame`.
- `url` - הכתובת שנכשלה.
- `elapsed_ms` - מספר המילישניות שהוקדשו לפני הוויתור.

הצורה נשמרת ב-`src/tests/test_grab_error_reporting.py`.

<a id="13-היסק-yolo26"></a>

### 1.3 היסק YOLO26

- **קלט:** פריים אחד + טבלה של ספי ביטחון לכל מחלקה.
- **פלט:** רשימת מילוני תיבות
  (`{cls, conf, x1, y1, x2, y2, cx, cy, w, h}`), כבר מסוננות רק
  למחלקות שאנחנו מעוניינים בהן.

המודל נטען פעם אחת בעליית התהליך. אם ה-IR של OpenVINO
(`yolo26m_openvino_model/`) קיים ליד `yolo26m.pt`, המנוע מעדיף אותו
להיסק ב-CPU: מהיר פי 1.8 בערך מ-PyTorch גולמי על מעבד ברמת Intel UHD
620. אם ה-IR חסר, המנוע נופל בחזרה ל-`.pt` באופן שקוף.

ספי הביטחון לכל מחלקה יושבים ברמת המודול של `detect_core.py`
כ-`DEFAULT_PER_CLASS_CONF`. ברירות המחדל שמרניות (0.22-0.35 בהתאם
למחלקה) כדי שהטרקר יראה קבוצה עליונה נקייה שממנה להתחיל טרקים. ראה
את [סעיף 3](#3-ספי-ביטחון-ושערי-תצוגה) לתמונה המלאה.

<a id="14-bursttracker"></a>

### 1.4 BurstTracker

- **קלט:** תיבות הפריים הנוכחי + מצב הטרקר מהפריים הקודם.
- **פלט:** אותן תיבות, כשלכל אחת מוטבע `track_id` יציב לאורך הפריימים
  של אותה סדרה.

`tracker.py` הוא טרקר פייתון טהור מבוסס תנועה בהשראת ByteTrack:

1. תיבות ביטחון גבוה (`conf >= 0.45`) תופסות טרקים באמצעות חיזוי
   מהירות קבועה + רדיוס התאמה של 30% מאלכסון הפריים.
2. תיבות ביטחון נמוך יכולות רק **להאריך** טרקים קיימים (רדיוס 15%);
   הן לעולם לא מתחילות טרק חדש.

טרקים גולשים על המסלול החזוי שלהם עוד `TRACK_MAX_MISSES = 2` פריימים
של אי-התאמה לפני שהם פורשים. המהירות מוחלקת ב-EMA עם משקל
`TRACK_VEL_SMOOTH = 0.6`.

<a id="15-ציור-השכבה-הפעילה"></a>

### 1.5 ציור השכבה הפעילה

רק שכבה אחת פועלת בכל רגע (אילוץ אופרטור). השכבה הפעילה צורכת את
התיבות ומייצרת את נתוני הציור שלה - תא בגריד החום, נקודה במסלול של
טרק, מלבן של פנים, חיתוך של לוחית וכו'.
`live_analysis.py::_publish_data` אוסף את הנתונים ל-JSON ואת הפריים
הגולמי ל-buffer של JPEG; ה-frontend דוגם את שניהם.

<a id="2-מכניקה-של-כל-שכבה"></a>

## 2. מכניקה של כל שכבה

כל שכבה היא קובץ אחד תחת `src/app/`. `live_analysis.py` מנהל את סדר
הציור (Heat קודם כדי שהתיבות ייצוירו מעל; Faces אחרון כדי שהמלבנים לא
יוסתרו על ידי מסלולים). המידע הסופי לציור + JSON טלמטריה קומפקטי
(מספרים לכל מחלקה, אזעקות, קריאות לוחיות) הם מה שה-frontend מקבל
בפולינג הרגיל שלו.

| שכבה       | קובץ                          | הערות |
| ---------- | ----------------------------- | ----- |
| `paths`    | `live_analysis.py` (inline)   | היסטוריית מסלול לכל טרק, מוגבלת ל-`TRAIL_MAX_PTS = 40` נקודות. רמת מהירות מבוססת על אורך גוף לשנייה. |
| `pose`     | `pose.py`                     | 17 נקודות COCO מלמעלה על חיתוכי אדם עם גובה תיבה מעל `KPS_MIN_BOX_H = 96 px`. |
| `gestures` | `gestures.py`                 | חלון זמני של keypoints; מפיק `hand_raised`, `both_hands_up`, `wave`. |
| `body`     | `live_analysis.py` (inline)   | דגלי קינמטיקה + מחוות לכל טרק אדם. |
| `faces`    | `faces.py`                    | YuNet של OpenCV. סף `FACE_SCORE = 0.60`, צלע מלבן >= 24 px. תוצאה ריקה על מצלמות רחוקות היא בכוונה. |
| `line`     | `cameras.py`, live_analysis   | קו ספירה מצויר בידי המפעיל. IN/OUT נקבע לפי היפוך סימן ביחס ל-A→B. |
| `loiter`   | `live_analysis.py` (zones)    | זיהוי שהייה בפוליגון עם קירור לכל טרק (רץ על מנוע האזורים של שכבת החניה). |
| `parking`  | `live_analysis.py` (inline)   | היפוך תפוסה על מקומות חניה שהמפעיל צייר + סריקה חוזרת של המקום כל 12 שניות. |
| `plates`   | `plates.py`                   | LPR דו-שלבי (yolov11-L + fast-plate-ocr cct_s_v2) עם מטמון לכל טרק, אינטגרציה מרובת-פריימים ושער דקדוק פר-מדינה. |
| `heat`     | `heatmap.py`                  | גריד 48x27, צבירת foot-point, דעיכה של חצי-חיים 180 שניות. |
| `fall`     | `live_analysis.py` (inline)   | חשד נפילה מבוסס יציבה: הטיית גו מעל 65 מעלות או תיבה שוכבת אחרי היסטוריית עמידה, אישור 2 טיקים. |

<a id="3-ספי-ביטחון-ושערי-תצוגה"></a>

## 3. ספי ביטחון ושערי תצוגה

ספי הזיהוי בנויים בשכבות:

1. **רצפת המודל** (`LIVE_CONF_FLOOR = 0.12`) - כל זיהוי מתחתיה
   נזרק מהמודל עצמו.
2. **שער לפי מחלקה** (`DEFAULT_PER_CLASS_CONF` ב-`detect_core.py`,
   כפול `LIVE_GATE_SCALE = 0.7` במסלול הלייב). מונע ממחלקות COCO
   שאין להן משמעות במצלמת רחוב ("רכבת" על גדר) לעבור.
3. **שער הטרקר** (`TRACK_HIGH_CONF = 0.45` ב-`tracker.py`). מעליו
   זיהוי יכול להתחיל טרק חדש; מתחתיו רק להאריך טרק קיים.
4. **שער התצוגה** (`DISPLAY_MIN_CONF = 0.32`,
   `DISPLAY_MIN_HITS = 1` ב-`live_analysis.py`). הציור מפרסם רק
   אובייקטים שאושרו על ידי הטרקר.

במחברת (סעיף 10) יש workflow של כיול שמאפשר לך לדגום פריימים מהמצלמה
שלך, לתייג את האמת בפועל, ולגזור עדכונים של ספי הביטחון לכל מצלמה
שנצרפים ל-`CAMERAS` בזמן ייבוא דרך `_merge_per_camera_conf()`.

<a id="4-ארכיטקטורת-ה-frontend"></a>

## 4. ארכיטקטורת ה-Frontend

`src/web/index.html` הוא דף סטטי אחד שמוגש על ידי שרת ה-HTTP. `app.js`
מטפל בתפריט המצלמות, בבניית האריח, בלולאת הניתוח וב-canvas שמעל
הוידיאו:

- **תפריט המצלמות** - מבקש `/api/catalog` ו-`/api/uploaded-videos`,
  ממלא את הרשימה הנפתחת. העלאת MP4/MKV מבצעת POST ל-`/api/upload-video`
  וטוענת מחדש את התפריט.
- **אלמנט הוידיאו** - שלושה מצבים לפי `cam.kind`:
  1. `local_file` -> `<video src>` שמוגש על ידי `/api/local-file`.
  2. `youtube` -> `<iframe>` שמטמיע את הנגן של YouTube.
  3. `hls` (או כל דבר עם `cam.hls`) -> `<video data-hls>` שמנוגן דרך
     `hls.js`.
- **לולאת הניתוח** (`beginTileAnalysis`) - יוצרת canvas שמעל הוידיאו
  ומבצעת פולינג ל-`/api/analysis/data?cam=<id>` כל
  `ANALYSIS_POLL_MS = 500 ms`. בין הטיקים של ה-backend היא מבצעת
  אינטרפולציה של מיקומי התיבות דרך מיזוג לינארי + הרחבת מיקום לפי
  מהירות. כאשר הוידיאו רץ, אלמנט ה-`<video>` / iframe שמתחת נראה
  וה-canvas מצייר תיבות מעליו. כאשר הוידיאו נעצר, JPEG חלופי
  (`<img data-analysis-bg>`) שמצויר על ידי ה-backend משתלט.

תקרת ההרחבה של הצד הלקוח: `EXTRAP_MAX_S = 3 s` ו-`EXTRAP_MAX_DIAG = 0.5`
(תיבה לא יכולה לזוז יותר מחצי אלכסון שלה בשנייה). מעבר לחלון הזה,
התיבה נדעכת עד שהטיק הבא של ה-backend מספק מיקום טרי.

<a id="5-נקודות-ה-api"></a>

## 5. נקודות ה-API

`src/app/dashboard_server.py` מגיש את התיקייה הסטטית `web/` בתוספת
נקודות ה-API הבאות:

| Endpoint                                     | תפקיד |
| -------------------------------------------- | ----- |
| `GET  /api/catalog`                          | קטלוג המצלמות (`active_cameras()`). |
| `GET  /api/uploaded-videos`                  | רשימת קבצי MP4/MKV שהועלו תחת `data/uploads/`. |
| `POST /api/upload-video`                     | העלאה multipart; הקובץ החדש מופיע כמצלמת `local_file`. |
| `GET  /api/ping`                             | probe יכולת שמחזיר `{ok: true, private: true}` ל-backend הפרטי. |
| `GET  /api/analysis/data?cam=<id>`           | ה-JSON של הטיק הנוכחי (תיבות, מסלולים, חום, אזעקות). |
| `GET  /api/analysis/frame?cam=<id>`          | JPEG חלופי של הטיק הנוכחי (fallback ל-video עצור). |
| `GET  /api/analysis/events?cam=<id>`         | טבעת אירועי אזעקה לצידונית הצ'יפים. |
| `POST /api/analysis/start?cam=<id>&layer=X`  | פותח (או מחליף) session חי על מצלמה `id` עם שכבה `X`. |
| `POST /api/analysis/stop?cam=<id>`           | סוגר את ה-session הפועל. |
| `POST /api/analysis/event/save?cam=<id>&id=` | שומר את הפריים המלא של אירוע אחד תחת `web/snapshots/detections/`. |
| `GET  /api/analysis/saved`                   | מניפסט של זיהויים שמורים (Investigation gallery). |
| `GET  /api/lines?cam=<id>`                   | קונפיג של קו הספירה עבור שכבת Line. |
| `POST /api/lines?cam=<id>`                   | שמירת קו ספירה שצויר על snapshot. |
| `POST /api/lines/clear?cam=<id>`             | הסרת override של קו למצלמה. |
| `GET  /api/zones?cam=<id>`                   | קונפיג פוליגונים של loiter / parking. |
| `POST /api/zones?cam=<id>`                   | שמירת פוליגונים שצוירו על snapshot. |
| `POST /api/zones/clear?cam=<id>`             | הסרת כל הפוליגונים למצלמה. |
| `GET  /api/crossings?cam=<id>`               | טבעת של אירועי חציית קו. |
| `GET  /api/heatmap?cam=<id>`                 | overlay heatmap מתמיד (JPEG מצויר או JSON). |

<a id="6-הוספת-מקור-וידיאו"></a>

## 6. הוספת מקור וידיאו

כדי להוסיף מצלמה שה-`kind` שלה כבר קיים, הוסף רשומה ל-`CAMERAS`
ב-`src/app/cameras.py` עם ה-`url` הנכון ואתחל את השרת. `/api/catalog`
יאסוף אותה אוטומטית.

כדי לתמוך ב-`kind` **חדש**:

1. הוסף branch ל-`resolve_stream(cam)` ב-`detect_core.py` שמחזיר
   כתובת נגינה או נתיב לקובץ עבור ה-kind החדש.
2. הוסף render ב-`app.js::buildVideoInto` אם צריך אלמנט נגן שונה
   (iframe, `<img>`, WebRTC).
3. אופציונלי: הוסף פונקציית עזר לחילוץ ב-`detect_core.py` (ראה את
   `resolve_skyline`, `resolve_webcamera24` לצורה).

<a id="7-הוספת-שכבה-חדשה"></a>

## 7. הוספת שכבה חדשה

1. צור `src/app/mylayer.py` שמייצא פונקציית `apply(frame, boxes, state)`
   שמעדכנת את `state` ומחזירה נתוני ציור.
2. רשום את שם השכבה ב-`LIVE_LAYERS` בתוך `live_analysis.py`.
3. חבר את הקריאה לציור בתוך `_publish_data` בצד השאר.
4. הוסף אפשרות רדיו ב-`web/app.js` תחת `ANALYSIS_LAYER_DEFS`.
5. הוסף את הציור על ה-canvas לנתוני הציור החדשים בתוך
   `_drawAnalysisOverlay`.

<a id="8-החלפת-מודל-הזיהוי"></a>

## 8. החלפת מודל הזיהוי

`MODEL_WEIGHTS` ב-`real_time_cv.ipynb` ו-`LIVE_MODEL_WEIGHTS`
(אם מוגדר) ב-`detect_core.py` שולטים באילו weights נטענים. אפשרויות
החלפה בסדר עולה של עלות:

- **yolo26x** - drop-in, +4.4 mAP מעל yolo26m, פי 2.4 latency לטיק
  על CPU. מומלץ כשיש GPU נבדל.
- **rtdetr-x** - detector מבוסס transformer, טוב יותר על עצמים
  קטנים / רחוקים (לוחיות רישוי ממצלמות רחוקות) אבל בערך פי 2
  latency מ-yolo26m וקובץ weights שונה לחלוטין.
- **rf-detr-large** - יותר מ-60 mAP אבל דורש GPU בפועל. `pip
  install rfdetr` + wrapper קטן ב-`detect_core.py`.

תמיד ייצא את ה-OpenVINO IR אחרי ההורדה:

```python
from ultralytics import YOLO
YOLO('yolo26x.pt').export(format='openvino', imgsz=640)
```

<a id="9-חקירה-ושמירת-זיהויים"></a>

## 9. חקירה ושמירת זיהויים

טאב Investigation מציג גריד מתמיד מ-`/api/analysis/saved`. כל רשומה
מפנה לקובץ JPEG של אירוע שמור תחת `web/snapshots/detections/`.
שמירה קורית בשתי דרכים:

- **ידני** - לחיצה על "save" בצ'יפ כלשהו בצידונית האירועים בזמן
  session חי. הפריים המלא של האירוע (`_full`) נכתב לדיסק ורשומה
  נוספת נדחפת למניפסט.
- **אוטומטי** - מכונת המצבים של `LiveSession._detect_events`
  פולטת אירוע לטבעת בכל שינוי מצב רלוונטי לשכבה (קריאה חדשה של
  לוחית, מחווה, אזעקת loiter, extreme_load).

המניפסט הוא `web/snapshots/detections/saved.json`, מוגבל ל-500
הרשומות הטריות ביותר.

<a id="10-מעטפת-ביצועים"></a>

## 10. מעטפת ביצועים

נמדד על Intel i5-8250U (4 ליבות, 8 threads, בלי GPU נבדל) עם OpenVINO
IR טעון:

| workload                              | טיק / latency          |
| ------------------------------------- | ----------------------- |
| yolo26m + Paths & speeds              | 0.8 - 1.5 שניות לטיק    |
| yolo26m + Pose                        | 1.5 - 3 שניות לטיק      |
| yolo26m + Plates (רכב אחד)            | 2 - 4 שניות לטיק        |
| שני sessions חיים במקביל              | לא נתמך (מגבלת session בודד - `MAX_SESSIONS = 1`) |

עם GPU נבדל, הטיקים בדרך כלל יורדים מתחת ל-200 מילישניות ותקרת
האינטרפולציה של ה-frontend (`EXTRAP_MAX_S = 3 s`) הופכת ללא רלוונטית -
תיבות תמיד נוחתות בתוך חלון ההרחבה.
